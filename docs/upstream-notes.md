## 2026-11-16 — libzmq 4.3.5 needs pkg-config to find a non-system libsodium

`builds/cmake/Modules/Findsodium.cmake` (generated by zproject) calls `find_package(PkgConfig REQUIRED)` before it looks for
sodium, so a libsodium fetched by CPM cannot be used on a machine without pkg-config, even when `SODIUM_INCLUDE_DIRS` and
`SODIUM_LIBRARIES` are already set. Workarounds in this repo (local only, per D4): `cmake/no-pkg-config.sh` answers
`--version` and reports no modules, and the two `SODIUM_*` paths are set as cache entries before libzmq is added. A system
libzmq built against libsodium needs none of this.

Two related notes:

- With `ENABLE_CURVE=ON`, libzmq requires `WITH_LIBSODIUM`; there is no tweetnacl fallback in the CMake build (the option
  exists in the autotools path only), so `WITH_LIBSODIUM=OFF` silently produces a CURVE-less library that accepts CURVE socket
  options with `EINVAL` — worth checking with a probe rather than trusting the build.
- A static libsodium linked into czmq/malamute's shared libraries must be built with `CMAKE_POSITION_INDEPENDENT_CODE=ON`,
  otherwise the link fails with `relocation R_X86_64_PC32 ... can not be used when making a shared object`.

**Not fixed upstream** (D4): recorded here for whoever hits it next.

## Finding: no peer key as message metadata

On this build, `zmq_msg_gets(msg, "User-Id")` returns nothing for messages received on a CURVE-enabled ROUTER in our
configuration, so a server cannot learn which key a client authenticated with from the message itself. CURVE peer pinning
therefore needs a ZAP handler (ZAP-1 style allow-list), which this project tracks as SEC-1b. Not reported upstream - possibly
our usage, possibly a documentation gap around when metadata is attached.

## Finding: libzmq's ZAP reply must be exactly seven frames

`src/zap_client.cpp` reads a fixed `zap_reply_frame_count = 7` and expects the last frame without `more`. The reply is
`[empty address delimiter]["1.0"][request id][3-char status code][status text][user id][metadata]`. A five-frame reply (the
obvious reading of RFC 27) fails the handshake with `ZMQ_PROTOCOL_ERROR_ZAP_MALFORMED_REPLY`, and from the application's side
that is indistinguishable from "the peer never connected" - no error surfaces on the socket that refused.

Also observed: the ZAP *request's* identity frame is empty for a connecting DEALER, so a handler cannot key a policy on the
peer's configured node id at handshake time. Pinning must fall back to the peer address or the key itself.

Not filed upstream (D4). Recorded because it cost real time and is not in the RFC text.

## Finding: a ZAP reply is SIX frames, not seven (my bug, not libzmq's)

I first concluded libzmq was rejecting a correct reply. It was not: I was sending an empty address-delimiter frame as the
first of seven, and REP sockets already hold the request's envelope and prepend it themselves. The extra frame shifted every
index libzmq checks, which surfaced as `ZMQ_PROTOCOL_ERROR_ZAP_MALFORMED_REPLY`.

The correct reply, matching czmq's `zauth`, is six frames:

```
"1.0" | request id | 3-char status code | status text | user id | metadata
```

The request, for reference, is `version, request_id, domain, address, identity, mechanism, credentials...` (seven for CURVE,
the last being the client's 32-byte public key).

Two other things cost time and are worth writing down:

- **The monitor is the only place the reason appears.** `ZMQ_EVENT_HANDSHAKE_FAILED_PROTOCOL` carries the protocol error in
  the event's *value* field, and `zmq_event_t` is packed: for a 6-byte event message the value sits at byte offset 2, not 4.
  Reading the wrong offset shows `0x2000` (the event id again) and looks like a libzmq bug.
- **The handshake does not know the peer's identity.** The identity frame is empty at ZAP time (identity is exchanged after
  the handshake), so a policy cannot key on a configured node id there. Pin by address in open mode, or check the presented
  key against a provisioned list in closed mode.

Not an upstream bug, and nothing to file. Recorded because the failure mode ("sleeps forever, no traffic, no error") gives no
hint about the cause.

## Finding: zgossip's actor API is public; its design is still wrong for this project

**Corrected 2026-11-21.** An earlier version of this note claimed `zgossip` emits private `zgossip_msg` frames to its caller, so
an application outside czmq could not parse what it receives. That was wrong, and the correction matters because the wrong claim
is a bad reason:

- `zgossip_msg.h` *is* private to czmq (`<class name="zgossip_msg" private="1" />` in `project.xml`, in `src/`, not installed),
  and some packagers strip even the copy a CMake build leaks into `include/`.
- But that frame format is only what `zgossip` speaks *on the wire between gossip nodes* (`ROUTER`/`DEALER`). To its own caller it
  sends plain strings on the `zactor` pipe: `zstr_sendx(self->pipe, "DELIVER", key, value, NULL)`, readable with `zstr_recvx`.
  Its own selftest consumes them that way. So commanding **and** listening are both public `czmq` API, exactly like `zbeacon`.

**Why Mosaic still does not use it** (the real reasons, which are stronger than the one above):

1. `zgossip` opens its own TCP sockets, outside `Transport` - so it bypasses CURVE `PeerPins`, the ZAP handshake policy, the
   per-peer request budgets and peer scoring. Discovery would become the one unauthenticated, unthrottled, unpenalised path in
   the system.
2. It never expires tuples, and `UNPUBLISH` deletes only locally: there is no distributed delete and no tombstone, so a dead node
   stays in every table forever unless the application layers its own TTL on top.
3. On every `CONNECT` it dumps the whole tuple table (`HELLO` then one `PUBLISH` per tuple) and floods every new tuple to all
   edges - czmq's own documentation limits it to slow-changing configuration.
4. Its CURVE support is behind `CZMQ_BUILD_DRAFT_API`, which most distributions disable.

Consequence for Mosaic: LAN discovery uses `zbeacon` (plain frames on the actor pipe), and second-hop discovery is Mosaic's own
`PeersMsg` over the existing `Transport` - which is what buys it the pin policy, the budgets and the scoring. See
[DISC-3](../openspec/specs/discovery/peer-discovery/spec.md) and [05](design/05-node-and-transport.md).

Not filed upstream (D4). Recorded because "we cannot read its output" was a satisfying-sounding reason and a false one: the
conclusion was right and the argument was not.
