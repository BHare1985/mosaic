# Malamute and Dafka: how each works (system design)

Written from the source in [references/](references/README.md)
(malamute `2c5ec20`, dafka `c2dc88d`), not only from their READMEs.
File names below are relative to `references/malamute/` and
`references/dafka/`. Where the docs and the code disagree, this doc says so,
because it changes what is worth reusing.

**Short version**

* **Malamute** is a *single-broker* messaging server with three patterns
  (streams, mailboxes, services). Its whitepaper (`MALAMUTE.md`) describes a
  much larger system than the code implements. The code is a small, in-memory,
  working core, and says so itself ("minimal, incomplete implementation",
  `src/mlm_server.c`).
* **Dafka** is a *brokerless* log: a full mesh of ZeroMQ PUB/SUB sockets,
  per-producer ordered partitions, passive LevelDB stores, and a
  "tower" used only for peer discovery. The implementation is closer to its
  README, with a few gaps listed in section 3.

## 1. Malamute

### 1.1 The gap it fills

The whitepaper's thesis (`MALAMUTE.md`): real systems need several
data-flow styles (live streams, replayable streams, direct messages,
service requests), usually served by separate products. Malamute
puts them behind one protocol and one broker, on ZeroMQ.

### 1.2 Architecture

```
 client A ──┐                      ┌── stream engine "weather" (zactor, own thread)
 client B ──┼─ ROUTER (tcp) ─ mlm_server ──┼── stream engine "news"
 client C ──┘   one process    │            └── ...
                              ├── mailbox engine (mlm_mailbox_bounded, zactor)
                              └── in-process service queues (per service)
```

* **One server process**, a state machine generated by zproto from
  `src/mlm_server.xml`. Each client has its own state: `start` →
  (`CONNECTION OPEN`) → `connected`. Anything else before OPEN is an error and
  the client is dropped.
* **Client side** (`src/mlm_client.*`) is a generated actor with a small
  blocking API (`set_producer`, `set_consumer`, `sendto`, `sendfor`,
  `recv`, ...).
* **Protocol** (`src/mlm_proto.xml`): `CONNECTION OPEN/PING/PONG/CLOSE`,
  `STREAM WRITE/READ/SEND/DELIVER/CANCEL`, `MAILBOX SEND/DELIVER`,
  `SERVICE SEND/OFFER/DELIVER`, `CREDIT`, `CONFIRM`, `OK`, `ERROR`.
  Clients identify with an address string; the server is addressed by endpoint.
* **Security:** CZMQ `zauth` with NULL or PLAIN, configured via
  `malamute.cfg` (`src/malamute.c`). No CURVE.
* **Config:** a `zconfig` file (`src/malamute.cfg.in`): timeout, bind
  endpoint, PLAIN passwords, mailbox and service queue size limits.

### 1.3 The three patterns, as implemented

| Pattern | Flow | Implementation facts |
|---|---|---|
| **Stream** (pub/sub) | `STREAM WRITE name` makes a client the stream's single writer; `STREAM READ name pattern` subscribes with a regex; `STREAM SEND subject content` publishes. | One stream = one `mlm_stream_simple` actor (one thread). Matching is a **linear scan of regex selectors** (`zrex_matches` per selector, `src/mlm_stream_simple.c:208`). **No journal, no replay, no persistence.** A late joiner sees only new messages. |
| **Mailbox** (direct, store-and-forward) | `MAILBOX SEND address subject content` queues to the address; when that client connects (and after each delivery) the server polls the mailbox. | In-memory queue per address (`src/mlm_mailbox_bounded.c`, `src/mlm_msgq.c`) with soft warn and hard byte limits. A message is **removed when handed to the server for delivery** (`QUERY` → `mlm_msgq_dequeue`), so there is no ack-before-delete. |
| **Service** (request distribution) | Workers `SERVICE OFFER name pattern`; requesters `SERVICE SEND name subject content`. | Per-service queue plus a list of offers; dispatch scans offers, matches the subject regex, sends to the first match and **moves that offer to the end** (a round-robin among matching workers). Undelivered requests wait in the queue (`s_service_dispatch`, `src/mlm_server.c`). |

All three share one client connection, one credit counter (in the protocol),
and one idle timeout (default 10 s, per `malamute.cfg.in`).

### 1.4 Reliability and flow control: spec vs. code

| Whitepaper says | Code says |
|---|---|
| Credit-based flow control: client sends credit, broker sends only as much (`MALAMUTE.md` "CBFC") | `CREDIT` is parsed and accepted, but **`credit_the_client()` is an empty function** (`src/mlm_server.c`). The server never checks credit. Only ZeroMQ's own high-water mark limits sending. |
| Mailbox and service messages are acknowledged; undelivered service requests are re-queued if the worker dies | `CONFIRM` is not implemented: `have_message_confirmation()` sets an exception and logs "message confirmations are not implemented". I found no re-queue code. |
| Streams are journalled; slow or late clients switch between live and replay | No journal exists. Nothing switches modes. |
| Inverted-bitmap subscription matching at ~2 µs per message | Not implemented; matching is regex-per-selector (see 1.3). The whitepaper's own header says it "does not describe an actual system". |
| Client connection liveness | **Implemented**: `PING/PONG`, expiry timer, `client_expired` → deregister. |
| Back-pressure on the mailbox / service queue | **Implemented**: byte-size limits with warn and refuse (`src/mlm_msgq.c`). |

### 1.5 What works well

* A tiny, readable server: one generated state machine, three engines.
* Clean separation: engines are zactors behind a message API
  (`STREAM.md`), so alternative stream engines (persistent, journalled) can
  plug in. Nobody has written one in this repo.
* Subject regex addressing for streams and services.
* Good fit for LAN, single-site integration where one broker is acceptable.

### 1.6 Limits

* Single broker: it is the bottleneck and the single point of failure.
  There is no clustering or federation in the code.
* No durability: restart loses mailboxes, service queues and streams.
* No delivery guarantees beyond TCP/ZeroMQ.
* No CURVE or per-topic ACLs; PLAIN auth only.
* Documentation is ahead of code, so treat `MALAMUTE.md` as a design
  wish-list.

## 2. Dafka

### 2.1 The gap it fills

From the README's "Design": Kafka's consumer groups need consensus, which makes
consumer and producer start-up slow (seconds). Dafka removes consensus and the
broker from the data path to get faster joins, lower latency and simple
operation, at the cost of group semantics.

### 2.2 Architecture

```
                 ┌──────────── tower (XPUB/XSUB, discovery only) ────────────┐
   beacon msgs   │                                                           │ re-broadcast
  {sender, host, port}  ───────────────►  XSUB ── forward ──► XPUB  ─────────┘ to all peers
                                                                  │
  every peer binds its own PUB and connects SUBs to every peer it hears about

  producer ──PUB──► consumers (SUB)        data path is peer-to-peer
      │       └────► stores    (SUB)
      ◄── ACK ── store (PUB/SUB)
  consumer ── FETCH/GET_HEADS ──► stores, producers  (all PUB/SUB)
  store ── DIRECT_RECORD/DIRECT_HEAD ──► consumer
```

* **Everything is PUB/SUB.** The protocol is declared `pubsub = "1"` in
  `src/dafka_proto.xml`: each message's first frame is a routing "topic" (an
  address or subject) so FETCH, ACK and DIRECT_* are *unicast by topic prefix
  over PUB/SUB*, not ROUTER/DEALER. This is why the data path needs no broker.
* **Discovery ("tower" + beacon).** Each peer binds a PUB to a random port and
  every second publishes a beacon `{sender, host, port}` to the tower's XSUB
  (`src/dafka_beacon.c`). The tower rewrites the host from the TCP peer address
  when the host is empty and republishes on its XPUB (`src/dafka_tower.c`).
  Every peer subscribes to beacons, then connects its SUB to each announced
  PUB. Result: a **full mesh** of PUB→SUB connections. The tower never sees
  records. It is a rendezvous service, **a single point of failure for
  discovery** (new peers cannot find each other without it; existing links
  survive). The README allows "one or more towers".
* **Roles** (each an actor): `dafka_producer`, `dafka_consumer`,
  `dafka_store` (a `store_writer` + `store_reader` pair), `dafka_towerd`
  (daemon).
* **Storage:** LevelDB. Keys are `(subject, address, sequence)` for records and
  `(subject, address)` for the head (`src/dafka_msg_key.c`,
  `src/dafka_head_key.c`, `src/dafka_store_writer.c`).
* **Identity:** a producer's `address` is a random UUID created per
  producer instance (`zuuid`, `src/dafka_producer.c`). **It is not a durable
  identity**: a restarted producer is a new partition.

### 2.3 Message flow

Grammar from `src/dafka_proto.xml`:

```
DAFKA         = join-consumer / publish / offsets
join-consumer = S:STORE-HELLO C:CONSUMER-HELLO *( S:DIRECT-HEAD [ consumer-fetch ] )
consumer-fetch= C:FETCH 1*( P:DIRECT-RECORD / S:DIRECT-RECORD )
publish       = P:RECORD [ consumer-fetch / store-fetch S:ACK ]
store-fetch   = S:FETCH 1*( ( P:DIRECT-RECORD / S:DIRECT-RECORD ) [ S:ACK ] )
offsets       = P:HEAD [ consumer-fetch / store-fetch ]
```

1. **Publish.** `s_publish` pushes the payload into an *unacked list* (chunked
   in-memory buffer, 256 records per chunk), assigns the next sequence number
   (starting at 0) and publishes `RECORD` to everyone. The first publish
   starts a **HEAD timer** (default 1000 ms, `producer/head_interval`)
   that periodically announces the latest sequence.
2. **Store.** The store writer subscribes to RECORD, HEAD and DIRECT_RECORD
   (the *direct* subscriber is polled first, so repair traffic wins over live
   traffic). It accepts a record only if `sequence == head + 1`; otherwise it
   drops duplicates or sends a FETCH for the gap. It writes batches to LevelDB,
   updates the head, then sends **one cumulative ACK per partition per batch**.
3. **ACK.** The producer's `dafka_unacked_list_ack(seq)` frees everything up
   to `seq`. Before freeing, **any single store's ACK is enough**. The README
   says producers keep records until "a configurable minimum number of
   stores" ack; I found no such setting in the producer or list code (the only
   producer settings are `head_interval`, `terminate_unacked`, `high_watermark`,
   `verbose`).
4. **Consumer.** Per `(subject, address)` it keeps the last delivered sequence
   (`sequence_index`). On RECORD/DIRECT_RECORD: if `seq == last+1` deliver; if
   `seq > last+1` send FETCH from `last+1` and **drop the out-of-order record**
   (no reorder buffer); if `seq <= last` ignore. On HEAD/DIRECT_HEAD ahead of
   its offset, FETCH. The first time it sees a partition, `consumer/offset/reset`
   (`latest` default, or `earliest`) sets the starting offset.
5. **Join.** A new consumer's SUB triggers each store's XPUB welcome (`W`) →
   `STORE-HELLO`; consumer replies `CONSUMER-HELLO` with its subjects, then
   `GET-HEADS`; stores answer `DIRECT-HEAD` per partition; the consumer
   FETCHes what it lacks.
6. **FETCH storm control.** `dafka_fetch_filter` dedupes identical FETCH
   requests with a 10 000-slot hash cache keyed by subject, address, sequence
   and the current second.
7. **Shutdown.** `$TERM` on a producer waits until all records are ACKed unless
   `producer/terminate_unacked` is set.

### 2.4 Guarantees (what the code supports)

* Per-partition order, gapless delivery to consumers (via FETCH repair) as long
  as *some* node (producer or a store) still has the records.
* Durability = at least one store has ACKed (with the caveat in 2.3.3).
* No cross-partition order.
* Consumers de-duplicate by sequence, so they never see repeats.
* No auth: I found no CURVE/ZAP use in `src/*.c`. Any peer that can reach
  the tower can join.

### 2.5 Limits

* Tower is a discovery single point of failure; the mesh is O(n²) in
  connections, which limits cluster size.
* **Every store stores every partition** ("each partition is replicated to
  each store", README) — replication factor is "all", no sharding.
* Producer identity is ephemeral (random UUID per run), so offsets are not
  tied to a durable writer.
* Out-of-order records are dropped and re-fetched, wasting bandwidth during
  catch-up.
* No retention or compaction found in the code I read.
* Last commit 2020; depends on LevelDB and CZMQ/libzmq draft APIs (the proto
  uses `zmq_msg_t` and peer-address frame metadata).
* No consumer groups, no transactions, no exactly-once. By design.

## 3. Claims in the supplied summaries, checked

Two third-party summaries of each project were supplied. Verdicts against
the code:

| Claim | Verdict |
|---|---|
| Malamute: "all the enterprise messaging patterns in one box" | **Design intent, partly delivered.** Streams, mailboxes and services exist; reliability for each does not (1.4). |
| Malamute records streams to a journal and switches clients between live and on-demand | **Whitepaper only.** No journal in code. |
| Malamute uses credit-based flow control so slow consumers are dropped, not back-pressured | **Whitepaper only.** `CREDIT` is accepted and ignored. |
| Malamute uses an inverted-bitmap matcher (~2 µs/message) | **Whitepaper only.** Regex scan per selector. |
| Malamute: acknowledged mailbox delivery; service requests re-queued when workers die | **Whitepaper only.** `CONFIRM` unimplemented. |
| Malamute: fair service dispatch via a mediated queue | **Partly.** There is a queue and rotation among matching offers, but no "worker ready" signal. |
| Dafka: drop-in Kafka replacement without consensus | **Design goal, yes.** Wire protocol is its own, not Kafka's. |
| Dafka: no broker in the data path; towers only connect peers | **Confirmed** (`src/dafka_tower.c`, `src/dafka_beacon.c`). |
| Dafka: consumers keep their own offsets; nobody else tracks them | **Confirmed** (`sequence_index` in `src/dafka_consumer.c`). In-memory only: offsets are lost when a consumer restarts, unless the consumer API persists them (I did not find that). |
| Dafka: producers buffer unacked records until a configurable minimum number of stores ack | **Not as described.** Buffering via `dafka_unacked_list` is real; a configurable minimum is not found; one ACK suffices. |
| Dafka: durability without consensus | **Confirmed**, with the limits in 2.4 and 2.5. |

## 4. What this means for Mosaic

Side by side:

| | Malamute | Dafka |
|---|---|---|
| Topology | star (one broker) | full mesh + discovery tower |
| Transport | ROUTER server, zproto protocol | PUB/SUB everywhere, topic-prefix addressing |
| Durability | none (RAM) | LevelDB stores |
| Replay / catch-up | none | HEAD + FETCH + stores |
| Flow control | specified, not implemented | PUB/SUB high-water marks; FETCH dedupe |
| Patterns | stream, mailbox, service | log only |
| Security | PLAIN | none |
| Maturity of code | small, maintained, builds | feature-complete core, abandoned 2020 |

Take from **Dafka**: the single-writer partition, RECORD/HEAD/FETCH/ACK loop,
STORE/CONSUMER hello handshake, the fetch filter, and the "direct subscriber
first" store trick. Take from **Malamute**: the generated-state-machine
protocol style, the pluggable engine boundary, mailbox/service semantics as
*optional layers on top of the log*, and the flow-control *idea* (implement it
for real, since Malamute did not).
Fix in our design: durable writer identity (keys, not UUIDs), a real
minimum-replicas rule, persisted consumer offsets, reorder buffering, CURVE,
and discovery that does not depend on one tower. See
[decentralized-broker-2026.md](decentralized-broker-2026.md).

One change to that doc follows from this reading: Dafka does not use ROUTER/DEALER
for repair. It uses PUB/SUB with address-prefixed topics. Either is viable;
ROUTER/DEALER is better for credits and flow control, and PUB/SUB keeps the
Dafka wire shape. Choosing between them belongs with decision 3 in
[direction.md](direction.md).
